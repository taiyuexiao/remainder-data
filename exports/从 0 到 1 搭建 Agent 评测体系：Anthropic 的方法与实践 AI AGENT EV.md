从 0 到 1 搭建 Agent 评测体系：Anthropic 的方法与实践 AI AGENT EVALS 从 0 到 1 搭建 Agent 评测体系： Anthropic 的方法与实践 同一个Agent跑10次结果不同，到底应该怎么评测？ #观远数据 #DecideX #AI 2026年1月， Anthropic团队发布了 《Demystifying evals for AI agents》， 把Agent评测 从基本结构、评分方法， 一直讲到如何从零建立评测体系。 今天我们就沿着这套方法讲清楚： Agent到底应该评什么、怎么评； 同一项任务多次运行结果不同，应该如何解释； 以及如何从 真实任务 和Badcase出发， 搭出第一套可以持续回归的Eval。 01 · DEFINE 一、先定义你到底在评什么 要搭建第一套 Agent Eval ，第一步不是选择评分模型，而是先定义自己到底在评什么。 传统大模型评测通常只有三个对象：Prompt、Response 和评分规则。但 Agent 会在多个回合中读取信息、调用工具、修改环境状态，并根据中间结果调整下一步动作。任何一步发生错误，都可能继续影响后面的执行。 因此， Agent 评测 面对的不是一段孤立回答，而是一条包含任务、执行轨迹和环境结果的 完整过程 。 一次完整的 Agent Eval ，可以先拆成四个问题。 测什么？ Task 是一项测试任务，需要包含明确输入和 成功标准 。 一次运行记录什么？ Agent 对 Task 的一次独立尝试叫 Trial 。Trial 中的模型输出、工具调用和中间结果构成 Transcript ；任务结束后，外部环境真正形成的最终状态叫 Outcome 。 谁来判断是否成功？ Grader 是针对某个评测维度的评分逻辑。同一个 Task 可以配置多个 Grader，分别检查结果、过程、质量与风险。 谁来运行整套评测？ Eval Harness 负责准备任务和环境、批量执行 Trial、记录轨迹、调用 Grader，并汇总最终结果。 这里还要区分两个容易混淆的概念。 Agent Harness 是让模型能够调用工具、维护状态并持续行动的系统； Eval Harness 则负责测试这个 Agent Harness 与模型组合后的表现。我们口中的“评测一个 Agent”，评的其实是模型、提示词、工具、 Agent Harness 和运行环境共同组成的完整系统。 多个具有共同目标的 Task 组合在一起，构成一套 Evaluation Suite 。例如，一套客服 Agent 评测 集可以同时覆盖退款、取消订单和升级处理。 — 评测 Agent，面对的是任务、行动、轨迹与结果组成的完整系统。原创示意图：煤球 02 · TASKS 二、从 20～50 个真实任务开始 知道评测由什么组成以后，下一步不是设计一个复杂平台，而是先建立第一批值得测的任务。 Anthropic 的建议是：不要等到积累几百条任务才开始。早期从 20～50 个 真实任务 起步，已经足以发现明显的行为变化。Agent 越成熟，才越需要更大、更难的评测集去捕捉细微差异。 任务也不应该凭空编写。最有价值的素材，通常已经存在于开发过程里：发布前反复进行的手工检查、Bug 记录、用户反馈和支持工单。真实发生过的失败，比团队想象出来的测试问题更接近用户风险。 收集到任务以后，需要把每个 Task 写到足够明确。一个实用判断标准是：两名领域专家独立阅读任务和 成功标准 后，能否得出相同的通过或失败结论。 如果专家自己都无法判断，Grader 也不可能稳定判断。 每个 Task 最好还要准备一份能够通过全部 Grader 的参考解法。它不仅证明任务确实可以完成，也能帮助你发现 Grader 是否配置错误。 Anthropic 还提醒，如果前沿模型尝试很多次仍然一次都没有通过，应当先检查 Task、环境和 Grader，而不是立刻断定模型没有能力。任务歧义、隐藏要求和评分漏洞，同样会制造看似合理的低分。 第一版 Task 至少要说清五件事： 01 输入与必要上下文是什么； 02 任务完成后，环境中应该出现什么结果； 03 哪些限制不能违反； 04 用哪些 Grader 判断结果、过程和质量； 05 每次 Trial 开始前，环境需要恢复到什么状态。 这五项明确以后，你才真正拥有一条可以反复运行的评测任务，而不只是一段用于“试试模型”的 Prompt。 03 · OUTCOME 三、优先检查 Outcome，再用 Transcript 解释原因 Agent 评测 最重要的一条原则，是优先验证任务结束后的真实结果，而不是只看 Agent 最后说了什么。 比如一个退款 Agent 告诉用户：“退款已经完成。”这句话只是 Transcript 的一部分。真正的 Outcome 是：退款记录是否产生、工单状态是否关闭，以及退款金额是否正确。 Outcome 回答“任务有没有完成”， Transcript 回答“为什么成功或失败”。这两个对象不能互相替代。 假设一个 Coding Agent 修复了认证漏洞，最终代码通过单元测试，说明 Outcome 基本正确。但查看 Transcript 后可能发现，它没有先读取认证逻辑，反而修改了多个无关文件，中间多次执行失败，最后只是偶然碰到一个能通过当前测试的实现。 只看 Outcome ，你会把这次任务判为成功；结合 Transcript ，你才能继续判断这种成功是否高效、安全，能否稳定复现。 但 Transcript 也不应该被写成唯一标准路径。Agent 可能找到评测设计者没有预料到、但对用户更好的解决方案。Anthropic 提到，Claude Opus 4.5 曾在订票评测中利用政策中的一条可行路径，为用户找到更好的方案，却因为没有遵循预设流程而被原 Grader 判为失败。 所以，能验证 Outcome 时，不要强迫 Agent 复刻唯一的执行路径。 Transcript 更适合用于诊断、效率和安全检查，而不是把所有正确方案提前写死。 — Outcome 判断任务有没有完成，Transcript 解释为什么成功或失败。原创示意图：煤球 04 · GRADERS 四、为不同问题选择不同的 Grader 当 Task 和 成功标准 明确以后，才轮到选择评分方式。 Anthropic 将 Agent Grader 分为三类：代码评分、模型评分和人工评分。它们不是三选一，而是分别处理不同性质的问题。 Code-based Grader ：验证确定性结果 代码评分包括单元测试、字符串匹配、静态分析、状态检查、工具及参数校验，以及轮数、Token 和延迟统计。 它速度快、成本低、结果客观，而且容易重复运行。文件有没有生成、数据库状态是否改变、代码能不能运行、是否调用了禁用工具，这些问题都应该优先交给代码。 它的弱点是规则相对刚性。只要 Agent 使用了规则没有覆盖的正确表达或新路径，就可能被误判。 Model-based Grader ：评价开放性质量 Model-based Grader ，也就是常说的 LLM-as-Judge ，更适合判断回答是否完整、结论是否得到证据支持、表达是否符合要求，以及研究报告有没有覆盖关键事实。 它比代码规则灵活，但也具有非确定性，成本更高，而且必须持续与人工专家校准。 Human Grader ：校准专家标准 人工评分包括领域专家审核、人工抽检、A/B 测试和多人一致性判断。它最接近真实用户和专家标准，却也最慢、最贵，不适合承担每次版本变更的全部评测。 更成熟的组合通常是：确定性 Outcome 优先交给代码，开放性和语义质量交给经过校准的 LLM Grader，再用少量人工评审持续检查 Judge 是否仍然符合专家判断。 不要把所有维度都塞给一个 LLM，让它给出一个无法解释的总分。 — 代码、模型与人工 Grader 各自处理不同性质的问题。原创示意图：煤球 不同类型的 Agent，也需要不同的 Grader 组合： Agent 类型 优先验证的 Outcome 补充检查 Coding Agent 代码能否运行、测试是否通过、旧功能是否被破坏 代码质量、安全扫描、工具使用 Conversational Agent 工单是否解决、退款是否真实完成 身份验证、轮数限制、金额限制、沟通质量 Research Agent 事实是否有来源、关键问题是否覆盖、数字是否准确 来源质量、综合分析与表达完整性 Computer-use Agent 数据库、文件、配置或订单状态是否真实改变 是否选择了合适的交互方式、操作效率与风险 这张表背后的原则很简单：先找可以确定性验证的结果，再为无法写成规则的质量维度补充模型或人工判断。 05 · RELIABILITY 五、一次通过，不能证明 Agent 可靠 无论使用哪一种 Agent，都绕不开非确定性。同一个 Task，这次 Trial 成功，下一次可能失败。 因此，一条 Task 通常需要运行多次。除了观察单次成功率，还可以用两个方向相反的指标理解 Agent 的能力与稳定性。 pass@k 衡量 Agent 尝试 k 次以后，至少成功一次的概率。k 越大，至少成功一次的机会越高。它适合允许多次探索的任务，例如同时生成多个方案，只要其中一个可用即可。 pass^k 衡量 Agent 连续运行 k 次、每一次都成功的概率。k 越大，全部成功的要求越难满足。它更适合用户期待每次都得到可靠结果的场景。 如果一个 Agent 的单次成功率是 75%，连续三次都成功的概率只有 0.75³ ，约等于 42%。 这两个指标揭示的是两个不同问题： pass@k 更接近能力上限， pass^k 更接近运行稳定性。一个 Agent 可能偶尔能够找到正确方案，却无法稳定复现这种能力。 所以在选择指标以前，先回答一个产品问题：这项任务允许多次尝试，还是要求每次都可靠？ — pass@k 关注至少一次成功，pass^k 关注每一次都成功。原创示意图：煤球 06 · REGRESSION 六、Capability Eval 与 Regression Eval 要分开 评测集不仅要告诉你当前表现如何，还要服务两种不同的开发目标。 Capability Eval 回答：“这个 Agent 现在能够做到什么？”它应该保留 Agent 暂时还做不好的难题，为能力提升留下空间。如果所有任务都能 100% 通过，这套评测就很难继续反映进步。 Regression Eval 回答：“Agent 原来已经会做的任务，现在还能不能稳定完成？”它的通过率应该接近 100%，一旦下降，就说明某些已经解决的问题可能重新出现。 当一条 Capability 任务经过多轮优化后能够稳定通过，它就可以进入 Regression Suite。它的身份从“我们能不能做到”，变成“以后还能不能继续做到”。 这意味着团队需要同时运行两套评测：一套推动能力边界向前，一套防止修复新问题时破坏过去已经解决的问题。 07 · PRACTICE 七、让第一套 Eval 变得可信 完成 Task、Grader 和多次 Trial，并不代表评测已经可靠。真正影响结果可信度的，往往是下面这些工程细节。 同时测试“应该发生”和“不应该发生” 如果只测试 Agent 该搜索时能不能搜索，最后可能优化出一个什么问题都去搜索的 Agent。评测集需要同时覆盖调用不足和调用过度，避免单向优化。 每次 Trial 都从 干净、隔离的环境 开始 上一次任务留下的文件、缓存、Git 历史或资源占用，都可能污染下一次结果。不同 Trial 如果受到同一个环境故障影响，它们就不再是独立样本。 这时测到的不是 Agent 能力，而是基础设施噪声。 优先验证产出，不要过度规定路径 复杂任务可能存在多条正确路径。评分规则如果把工具调用顺序写得过死，很容易把合法的新方案误判为失败。除非过程本身涉及安全、合规或成本风险，否则应当优先验证 Agent 最终产出了什么。 为复杂任务保留部分得分 一个退款 Agent 正确识别问题并完成身份验证，但最终退款失败，仍然比第一步就失败的 Agent 完成得更多。部分得分能够让评测结果反映这种差异，而不是把所有任务压成简单的 0 和 1。 持续校准 LLM-as-Judge Rubric 应把不同维度拆开判断，不要让同一个 Judge 一次评价所有方面。证据不足时，还应该允许它返回 Unknown ，而不是强迫模型猜一个分数。 LLM Grader 需要定期与人工专家结果对齐。只有当两者长期保持一致，模型评分才适合承担更大规模的自动评测。 定期阅读 Transcript 如果只看汇总分数，你无法判断失败来自 Agent 本身、任务描述歧义、Grader 错误，还是 Eval Harness 限制了模型。 Anthropic 的原则是：在没有检查评测细节和运行轨迹之前，不要直接相信一个评测分数。 持续维护评测集 Capability Eval 一旦接近饱和，就需要加入更困难的任务； Regression Eval 则要不断吸收新发现和已修复的 Badcase。 评测集不是一次性交付物，而是一项需要长期负责人和持续维护的工程资产。 把整条路径压缩成一份执行清单，就是： 01 从真实失败和手工检查中收集 20～50 条初始 Task； 02 为每条 Task 写清 成功标准 ，并准备参考解法； 03 为每次 Trial 建立干净、隔离的运行环境； 04 优先定义可验证的 Outcome ，同时完整记录 Transcript ； 05 按维度组合代码、模型和人工 Grader； 06 多次运行同一 Task，分别观察能力上限与稳定性； 07 将难题放进 Capability Eval ，将稳定通过的任务沉淀进 Regression Eval ； 08 持续阅读轨迹、修正 Grader，并吸收新的生产 Badcase。 — 从真实失败出发，逐步建立可以长期维护的评测体系。原创示意图：煤球 做到这一步，你已经拥有第一套能够运行、解释结果并持续演进的 Agent 评测 体系。 08 · PRODUCTION 八、自动评测不能替代生产反馈 再完整的自动化 Eval，也无法独立代表真实产品表现。 自动评测适合在上线前，以及每次代码、提示词或模型变更时快速运行；生产监控负责发现真实流量中的分布漂移和未知问题；A/B 测试用来验证改动是否真正改善用户结果；用户反馈则会暴露设计者没有预料到的失败。 人工阅读 Transcript 和系统化专家评审，帮助团队理解自动指标背后的原因。 这些方法不是互相替代，而是像安全工程里的多层防线一样，共同构成对 Agent 表现的完整判断。 Agent 评测 真正困难的，不只是模型具有随机性，也不只是 LLM-as-Judge 不够稳定。更根本的原因是，我们需要评测的本来就不是一段孤立回答，而是一条包含多次决策、工具调用、状态变化和环境结果的完整执行过程。 真正可靠的评测体系，也不是一次搭完的测试脚本。它会随着产品、模型和真实用户问题不断变化，并最终成为 Agent 开发过程中的长期基础设施。 REF · SOURCES 资料来源 01 Anthropic Engineering：Demystifying evals
